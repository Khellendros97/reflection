# 技术验证报告 01 · 项目导入 → 资产生成

> **要验证的问题**：能不能把「一个真实的前端项目」直接导入，自动生成可用的动画场景资产？
>
> **结论：可行，且成本比预期低。** 但确定性有一条容易被忽略的前提，以及四个真实踩到的坑。

## 二、核心机制：无侵入接管 Tauri IPC

### 原理

`@tauri-apps/api/core` 的 `invoke` 实现只有一行（`node_modules/@tauri-apps/api/core.js:201`）：

```js
async function invoke(cmd, args = {}, options) {
    return window.__TAURI_INTERNALS__.invoke(cmd, args, options);
}
```

所以只要**在页面脚本之前**定义 `window.__TAURI_INTERNALS__`，就能接管目标应用的全部后端调用。

### 落地方式

CDP 的 `Page.addScriptToEvaluateOnNewDocument`（agent-browser 里对应 `--init-script`）。

**不改目标项目一行代码**，也不需要在 Vite 里配 alias 或写插件。

### 证据

注入前：`http://localhost:1420/#/settings?reason=missing-config`（后端未就绪，走缺配降级分支）
注入后：`http://localhost:1420/#/welcome`（`is_config_complete` 返回 true，走正常流程）

### 为什么这条重要

AIShell 是 Tauri 应用，**这类应用的前端和后端是编译在一起的**，常规思路会认为「必须先跑起整个桌面应用才能采集」。实测证明不需要 —— 前端本身与 Tauri 解耦，只要供应数据就能独立渲染。

对产品的含义：**任何 Tauri / Electron 应用，只要能跑 dev server，就能被采集**。

## 三、确定性：结论与陷阱

这是本次验证最有价值的部分。

### 3.1 结果

| 对比 | 差异像素 | 最大通道差 | 说明 |
|---|---|---|---|
| 同一页面连拍（600ms 间隔） | 0 | 0 | ✅ 光栅化稳定 |
| **三次独立加载**（补全 mock 后） | **16 / 1296000**（0.0012%） | **1/255** | 肉眼不可辨 |
| 补全 mock **之前**的三次加载 | 32942 | 196 | ❌ 见 §4.1 |
| 离线快照 vs 在线采集 | 28 | 23 | ✅ |

差异全部集中在 **SVG 图标边缘与渐变 Logo** 的抗锯齿像素上，放大 8 倍肉眼仍不可辨（见 `spike-out/jitter-zoom.png`）。

### 3.2 关键前提一：必须用「静止判定」，不能用固定等待

固定等 2.5 秒和等 7.5 秒，画面**不一样**（差 32942 像素）。等 7.5 秒之后才稳定。

正确做法是**连拍直到两张截图字节相同**：

```js
let prev = await shot();
while (elapsed < maxWait) {
  await sleep(300);
  const next = await shot();
  if (next === prev) return next;   // 静止
  prev = next;
}
```

实测静止判定耗时 **400–1000ms**，比盲目等 7.5 秒快得多，而且**可靠**。

> 📌 这条对架构文档是硬修正：采集器的核心机制应该是 quiescence detection，而不是 `sleep(N)`。

### 3.3 关键前提二：「hash 相同」是错误的验收标准

架构文档里写的验收标准是「同一时间线两次渲染逐帧一致（可校验 hash）」。**实测达不到，也不应该要求达到** —— Chrome 的抗锯齿在不同加载间会有 1/255 级别的抖动。

正确的验收标准应该是：

```
结构性一致（硬门禁）：
  · DOM 节点数与树形结构一致
  · 所有锚点定位一致（几何漂移 = 0）
  · 计算样式中的颜色/尺寸 token 一致

像素级一致（阈值）：
  · 差异像素 < 0.1%
  · 最大通道差 ≤ 32
```

**结构一致是可达的且必须硬门禁；像素字节相等是伪目标。**

## 四、四个真实踩到的坑

### 坑 1：mock 的缺口不会「安静地少显示一点」，而是变成随机的不稳定

漏配 `sessions_get` 时返回了 `null`，应用在 AI 面板里 `.filter()` 崩掉、弹出错误横幅，4 秒后又消失。

后果：同一页面在 2.5s 与 7.5s 两个时刻的画面**差了 32942 像素（Δ196）**。

> **教训**：mock 表的完整性**直接决定确定性**。采集器必须把「未覆盖的 IPC 命令」当作**硬门禁**列出来，而不是用名字猜一个空值糊过去。
>
> 产品行为建议：未覆盖命令数 > 0 时，采集结果标记为「不可用于出片」。

### 坑 2：组件内部 catch 掉的错误会「烧进画面」

第一版采集器只检测 `Runtime.exceptionThrown`（未捕获异常），报告显示 **0 异常** —— 但离线快照里赫然有一条错误横幅。

因为错误被组件内部的 try/catch 吃掉了，只留在 DOM 里。

> **教训**：需要第三道检测 —— **扫描画面内的错误文案**（`失败|错误|异常|Error|undefined|null` 等关键词）。
>
> 这比异常检测更贴近「用户能看到什么」。

### 坑 3：`cloneNode` / `outerHTML` 不保留表单的 DOM 属性

在线渲染时 AI 模式下拉框显示「工作」，导出的快照里变成「仅建议」（第一个 option）。

原因：HTML 序列化只保留 **attribute**，不保留 JS 通过 **property** 设置的状态：

| 丢失项 | 表现 |
|---|---|
| `input.value` | 输入框内容丢失 |
| `select.value` / `option.selected` | **下拉框显示错误选项** |
| `checkbox.checked` | 勾选状态丢失 |
| `element.scrollTop/Left` | 滚动位置丢失 |
| `<canvas>` 像素 | 完全丢失 |

修法是在序列化前逐个写回属性，实测本次快照修复了 **22 处表单状态**。修复后离线差异从 276 像素（Δ136）降到 28 像素（Δ23）。

> **教训**：快照必须有一个「状态修复 pass」，不能直接 `outerHTML` 了事。canvas / video / iframe 更是完全无法这样处理，必须另想办法（见 §7）。

### 坑 4：Chrome 端口被残留进程占用，会静默连到旧实例

固定调试端口 + `proc.kill()` 只杀父进程（Chrome 会派生一堆子进程），导致端口被僵尸进程占住。新实例绑定失败，脚本**静默连到旧浏览器**，然后卡死。

> **教训**：调试端口随机化 + `taskkill /T /F` 杀进程树。这类问题表现为「莫名卡住」，排查成本很高。

## 六、成本评估

| 项 | 实测 |
|---|---|
| 单页采集耗时 | **~2 秒**（不含 Chrome 启动 ~4 秒） |
| 静止判定耗时 | 400–1000 ms |
| 首次为一个项目补齐 mock 表 | **约 1 小时**（31 个命令） |
| 后续新增页面 | 增量补命令，边际成本快速下降 |
| 代码量 | 采集器 4 个文件、约 600 行 |

> **主要成本在 mock 表，不在采集技术。** 采集机制本身已经跑通且稳定。
>
> 反过来看这是个好消息：mock 表可以**复用**——同一个项目的所有页面共享一张表，而且 AI 可以辅助生成（给它命令名 + 预期类型清单）。

## 七、尚待验证（诚实清单）

| # | 未验证项 | 风险 | 建议下一步 |
|---|---|---|---|
| V1 | **多路由批量采集** | 中 | 遍历路由逐个采集，合并成多场景资产 |
| V2 | **交互后的状态**（点进工作台、打开对话框） | **高** | 这是演示视频的主战场，必须验证「执行动作 → 稳定 → 采集」 |
| V3 | **Web 字体** | 中 | 本次 `@font-face` 为 0（用的是系统字体）。换成 Web 字体后必须验证字体内联与度量一致 |
| V4 | **Canvas / WebGL / 视频** | **高** | 快照技术完全无法处理，需要 `toDataURL` 快照或改为运行时渲染 |
| V5 | 非 Tauri 应用（Electron / 纯 Web） | 低 | Electron 走同一套 `__TAURI_INTERNALS__` 思路不适用，但可注入各自 IPC 层；纯 Web 拦截 `fetch` 即可 |
| V6 | 运行时场景（保留应用 + mock，可驱动状态） | **高** | 本次只验证了**静态快照**。架构文档 ADR-003 主张的「运行时场景 + 操作重放」还没验证 |
| V7 | 组件库差异（Vue / Svelte） | 低 | 选择器生成与框架无关，预期成立 |

### 对 V6 的说明（最重要的一条）

本次验证走的是**静态快照**路线：去掉所有脚本，冻结成一帧 HTML。

它能证明「资产化可行」，但**不能驱动状态** —— 而演示视频恰恰需要状态变化（点击后页面变了）。

架构文档主张的**运行时场景**（保留应用 + mock，通过操作重放驱动状态）**尚未验证**。这是下一步最该做的事：验证「在一个采集好的场景里点击 → 状态正确变化 → 能稳定截图」。

## 八、对架构文档的修正建议

| # | 修正 | 理由 |
|---|---|---|
| 1 | 验收标准：**「hash 相同」→「结构一致 + 像素阈值」** | 实测抗锯齿抖动无法消除，且无必要 |
| 2 | 新增：**静止判定（quiescence detection）** 作为采集器核心机制 | 固定等待既慢又不可靠 |
| 3 | 新增：**mock 覆盖率硬门禁** | 未覆盖命令 > 0 时必须拒绝出片 |
| 4 | 新增：**画面内错误文案检测** | 组件内 catch 的错误会烧进画面 |
| 5 | 新增：**表单 / 滚动状态修复 pass** | `outerHTML` 不保留 property 状态 |
| 6 | 明确：**静态快照 vs 运行时场景**两条路线及其取舍 | 本次只验证了前者，后者是主战场 |
| 7 | 渲染后端章节补一句：**采集器本身与 Remotion 无关** | 采集产物是 HTML + 锚点表，可用任何渲染器消费 |

## 十、最终判断

**「直接把项目导入生成资产」是可行的，而且比预想中干净。**

- 技术上：无侵入接管 + 自动锚点 + 自包含导出，全部跑通
- 成本上：主要成本是 mock 表（一次性、可复用、AI 可辅助）
- 质量上：离线快照与在线渲染差 28 像素（0.002%），锚点 26/26 精准

**但必须修正一个认知**：真正难的不是「采集」，而是「**让页面静止下来**」。

mock 覆盖不全 → 异步错误 → 页面永远静不下来 → 画面不确定。
这条因果链是本次验证最重要的发现，它把「mock 覆盖率」从一个实现细节提升成了**产品级硬门禁**。
