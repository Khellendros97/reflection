## 二、决定性的那条：逐帧重放契约

Remotion 逐帧渲染时，**每一帧都可能是一个新的渲染进程**。所以运行时场景必须满足：

```
State(k) ≡ 全新加载页面 + 从零重放前 k 个动作
```

如果不能，就无法逐帧渲染，运行时场景这条路直接死掉。

### 实测

| k | 动作 | 重放指纹 | 顺序执行指纹 | 一致 | 加载+重放耗时 |
|---|---|---|---|---|---|
| 0 | （初始） | `f443677c` | `f443677c` | ✓ | 2269 ms |
| 1 | 仪表盘 | `9854cdc0` | `9854cdc0` | ✓ | 3415 ms |
| 2 | 文件资源管理器 | `caea2e9e` | `caea2e9e` | ✓ | 4513 ms |
| 3 | 服务器列表 | `416b8ca4` | `416b8ca4` | ✓ | 5642 ms |
| 4 | 命令收藏 | `2d17c3d8` | `2d17c3d8` | ✓ | 6701 ms |
| 5 | 历史命令 | `99f42261` | `99f42261` | ✓ | 7835 ms |

**契约成立。** 状态是「动作前缀」的纯函数 —— 架构文档 ADR-003「状态由操作重放得到」得到实证。

### 但性能不可接受（必须优化）

朴素实现 **约 5 秒/关键帧**，且线性增长。如果逐帧都这样，1800 帧要 2.5 小时。

架构文档 §9.3 已经预判了这个结构，现在有了真实数字：

| 层 | 要求 | 现状 |
|---|---|---|
| **契约层** | 必须能从 0 重放 | ✅ 已验证 |
| **优化层** | 进程内增量推进 | ❌ 未实现 |

Remotion 渲染同一 chunk 时帧号单调递增，可以只补差；**只有进程重启时才需要全量重放**。全量重放的次数 = chunk 数（通常几十），而不是帧数（上千）。

> 📌 **契约成立是必要条件，优化是工程问题。** 先有你才能优化；没有优化，这条路走不通。这个顺序很重要。

另外成本可压缩的空间：
- 采集时用 dev server，生产时用**预构建产物**，加载会快一个数量级
- 静止判定的 `minWait` 在「已知动作后必静」的场景可以调小
- 动作之间的等待可以并入渲染帧号调度，不必每次独立等

## 三、三个新发现

### 发现 1：锚点漂移有两种，必须分开处理

验证器抓到的第一个问题：点击「文件资源管理器」**画面没变化**。

排查结果：它的选择器是

```
#activity-bar > div.activity-icon.active:nth-of-type(3)
                          ^^^^^^^ 状态类
```

`仪表盘` 激活时，`文件资源管理器` 元素不再带 `.active`，`querySelector` 直接返回 `null`，点击落空。

**修法**（已实现）：选择器生成改为「语义属性优先、状态类一律剔除」：

| 优先级 | 策略 | 例子 |
|---|---|---|
| 1 | id | `#proj-search` |
| 2 | **稳定语义属性** | `div[title="文件资源管理器"]` |
| 3 | 结构路径（剔除状态类） | `#activity-bar > div.activity-icon:nth-of-type(3)` |

每个候选都必须「当前文档中唯一」才采用。

修完之后 Q1 从 4/5 变成 **5/5**。

**但漂移检测又抓出了第二类**：切到仪表盘后，`新建文件 / 新建目录 / 刷新` 三个锚点全部失配。

这次**不是选择器的问题** —— 那些按钮确实**不存在了**（文件树面板被卸载）。

> **结论：锚点漂移有两种，产品必须分开处理**
>
> | 类型 | 原因 | 处理 |
> |---|---|---|
> | **选择器脆弱** | 选择器里混入了状态相关的东西 | 采集期修复（已实现） |
> | **元素本就不存在** | 状态切换导致组件卸载 | **不是错误**，需要给锚点声明「在哪些状态下有效」 |
>
> 第二条意味着 Scene Bundle 需要一个**状态机模型**：锚点不是全局唯一的，而是绑定到状态。
> 时间线上「点击 `新建文件`」这个动作，必须同时记录「此时应处于 文件资源管理器 状态」。
>
> 这正是 `video/src/components/anchors.tsx` 里那条硬约束的运行时版本：
> *「锚点元素必须在消费方整个可见窗口内保持挂载」*。

### 发现 2：`cursor:pointer` 扫描不可少，但必须配两条过滤

第一版锚点枚举只认语义选择器（`button` / `[role]` / `[tabindex]`），抓了 **26 个**。

但 AIShell 的**活动栏 9 个导航图标全部漏掉** —— 它们是 `<div onClick>`，没有 role、没有 tabindex。而它们恰恰是演示视频最需要的操作入口。

加上「可见 + `cursor:pointer` + 尺寸合理」的补充扫描后变成 **82 个** —— 但**一半是噪声**：`svg` / `path` / `rect` / `circle` 这些 SVG 内部节点因为继承到 `cursor:pointer` 而被误收。

再加两条过滤后收敛到 **38 个有意义的锚点**：

| 过滤 | 规则 |
|---|---|
| 只保留最外层 | 若某候选的祖先也在候选集里，丢弃它（`svg` 之于 `div[title]`） |
| 必须有语义标签 | 匿名的 pointer 元素不要 |

> **26 → 38，多出来的全是活动栏导航；过滤掉了 44 个噪声。**
> 没有补充扫描会漏掉最关键的入口，没有过滤会得到一张不可用的表。

### 发现 3：状态切换是对的，但内容是 mock 的责任

点击「仪表盘」后，活动栏高亮正确切换、侧栏标题正确变成「仪表盘」—— **状态驱动完全正常**。

但面板内容是空的，因为 `dashboard_render` 的 mock 返回了 `{ charts: [] }`。

> **状态 ≠ 内容。** 驱动状态是采集器的活，填充内容是 mock 表的活。
> 这与报告 01 的结论一致：**主要成本在 mock 表**，它是内容创作，不是技术难点。
>
> 好消息是 welcome / settings 两条路由已经用 mock 数据渲染出了丰富内容（项目卡片、服务器列表、表单），证明了这条路径。

### 过程中被验证器抓到的失配

```
k=1 → ⚠ 漂移 2 失配：新建文件, 新建目录          （选择器含状态类 → 已修）
k=3 → ⚠ 漂移 3 失配：新建文件, 新建目录, 刷新    （面板卸载，元素不存在 → 状态语义）
```

> 这个「锚点漂移检测」本身就是一个应该产品化的功能：
> **每步之后回查所有锚点选择器是否还唯一命中，把失配的锚点标出来。**
> 它同时也是时间线编辑器的「锚点失配告警」的实现方式。

## 六、路线一 vs 路线二：定位建议

路线一走通了，但**路线二不是备胎，是补充**。

| | 路线一 · 运行时采集（L2） | 路线二 · AI 克隆（L3） |
|---|---|---|
| 保真度 | **最高**（就是真实界面） | 中高（AI 重绘，可能失真） |
| 可驱动 | ✅ 已验证 | 取决于生成的代码质量 |
| 成本 | mock 表（一次性、可复用） | AI 调用 + 人工校对 |
| 适用 | **有可运行前端的项目** | ① 没有可运行前端（只有截图/设计稿）<br>② 登录态/依赖复杂采不动<br>③ 需要「更干净」的示意场景 |
| 风险 | 依赖项目可运行 | 保真度不可控，需要还原度评分兜底 |

**建议**：架构文档 §7.3 的四档策略（L1 截图 / L2 采集 / L3 AI 重写 / L4 AI 生成）保持不变，**L2 为主路径，L3 为补充**。这次验证给 L2 补上了「可驱动 + 可逐帧重放」的证据。

一个具体的互补场景：**用 L2 采集真实界面作为「底」，用 L3 生成干净的分镜幕（片头/数据卡/标语）**。两者在同一时间线上混用。

## 九、最终判断

**「采集 → 驱动 → 逐帧复现」这条链路是通的。**

- 动作驱动：5/5 生效
- 再次静止：350ms 收敛
- 序列复现：逐步指纹一致
- **逐帧重放：State(k) = replay(前 k 个动作)，k=0..5 全一致**

**但有两件事必须做，否则落不了地：**

1. **增量推进**（V8）：契约成立 ≠ 性能可用。5s/关键帧必须优化到「只在进程重启时全量重放」。
2. **锚点的状态有效性**（V10）：面板卸载是正常状态切换，不是漂移。锚点必须知道自己属于哪个状态。

**一个可以立刻写进架构文档的经验**：

> 采集器抓到的每一个「点击没反应」，都要先问两个问题 ——
> **是选择器找错了元素，还是那个元素本来就不该存在？**
> 前者是采集器 bug，后者是状态语义。把两者混为一谈，锚点表就废了。
